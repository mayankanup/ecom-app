# payment-service

A local stand-in for a third-party payment gateway like Stripe — the way teams typically simulate a vendor like Stripe in dev/CI rather than hitting the real thing. Runs on **http://localhost:8081**.

## Why it looks like this

It deliberately mirrors Stripe's real, publicly-documented API conventions rather than inventing a bespoke shape, so it's recognizable to anyone who's integrated Stripe:

- `POST /api/v1/charges` — Stripe's own charges endpoint path
- `Authorization: Bearer sk_test_...` — Stripe's API key convention (a missing/wrong key gets a real-looking 401)
- Request: `{"amount": 2999, "currency": "usd", "source": "4242424242424242"}` — `amount` in minor units/cents, like Stripe
- Response mirrors a Stripe charge object: `{"id": "ch_...", "amount": 2999, "currency": "usd", "status": "succeeded", "created": 1700000000}`
- Uses Stripe's own real test card numbers: `4242424242424242` → `succeeded`, `4000000000000002` (Stripe's generic-decline card) → `failed`. Any other card number succeeds.

No persistence, no real payment processing — it's deterministic and stateless, purely for exercising the checkout flow and the Pact contract below.

## Running

```bash
./mvnw spring-boot:run
```

On Windows PowerShell, use `.\mvnw.cmd spring-boot:run`.

## Running the tests

```bash
./mvnw test
```

This runs the unit test for the approve/decline logic, a controller test for the auth/validation paths, and **the Pact provider verification test** — which needs the contract file at `../pacts/backend-payment-service.json` to already exist. That file is generated by `backend`'s consumer test, so **run `cd backend && ./mvnw test` (or at least `-Dtest=PaymentClientPactTest`) at least once before running this module's tests**, otherwise the provider verification has nothing to verify against.

See the root [README.md](../README.md#pact-contract-testing) for the full Pact picture (why file-based sharing instead of a Pact Broker, what each side asserts, how CI orders the two steps).
